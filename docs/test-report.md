# 测试设计与评估报告

## 一、测试设计方法

以**白盒方法**为主，黑盒方法为辅：

- **白盒**：先画出各函数控制流，按「语句覆盖 → 判定覆盖 → 条件覆盖」逐级
  设计输入，保证每个分支至少被走到一次；核心算法额外用**对拍**验证（见 §三）。
- **黑盒**：边界值分析（空串、单字符差异、恰好达到预算阈值）与等价类划分
  （正常 / 空 / 异常 / 超大四类输入）。
- **工具**：pytest + pytest-cov（coverage.py）。

## 二、用例清单

54 个用例，按模块分组：

| 文件 | 主要覆盖内容 |
|---|---|
| `tests/test_preprocess.py` | 归一化：丢标点、保留扩展区汉字、`keep_latin`、空输入 |
| `tests/test_similarity.py` | 18 个主用例（空/完全相同/无关/子集/打散/对拍等）+ 口径开关、非法口径、分块估计边界 |
| `tests/test_io_utils.py` | 编码自适应（GBK / BOM / UTF-16 / 乱码兜底）、目录报错、两位小数写出 |
| `tests/test_main.py` | 端到端、参数校验（个数/非法口径/文件不存在/目录）、无 stdout、verbose、兜底捕获 |
| `tests/test_performance.py` | 10 万字输入 < 5 秒（性能回归） |

18 个主用例与开发计划 §五 的用例表一一对应（`test_case01` ~ `test_case18`），
其余为补充的分支覆盖用例。

关键白盒覆盖点：

- `lcs_length` 的空串早退分支、滚动数组两种转移分支；
- `normalize` 的 `keep_latin` 真假分支；
- `decode_bytes` 的 BOM 判定分支、`utf-8`/`gb18030` 回退分支、`replace` 兜底分支；
- `_describe_os_error` 的四种 OSError 分支（含 Windows 下 errno 自动映射的坑）；
- `main` 的「正常 / InputError / 未预期异常」三条路径；
- `chunked_common_length` 的预算反解、空串、完全相同、上界不越界。

## 三、正确性对拍

`lcs_length_dp` 与 `lcs_length_bitparallel` 是同语义的两种实现。测试里内置一个
**独立的二维 DP 参照**（`tests/helpers.py::brute_force_lcs`），对随机串逐一对齐，
保证两个实现都正确——不是"自己验证自己"。

## 五、测试充分性自评

**这些测试用例能满足该程序测试的要求吗？—— 对"程序能否在各种输入下正确、
稳定、按时给出答案"这一目标，是充分的。** 理由如下：

- **覆盖到了什么**：功能上覆盖「正常 / 空 / 异常 / 超大」四类输入；接口上
  覆盖参数解析、编码回退、文件 IO 异常三条最易崩的路径；算法上同一份逻辑
  用「对拍」和「手算基准」两种独立方式交叉验证。
- **性能目标可测**：性能回归测试把"10 万字 < 5 秒"从一句口号变成一条会失败的
  断言——改进前它是红的，改进后转绿，本身就是改进证据。

**还有三点没覆盖，以及为什么可以接受：**

1. **答案"准不准"没有权威标准值**。出题方未公布各测试点的预期重复率，所以
   回归用例只能验证"落在合理区间 / 与手算基准一致"，无法验证"等于某个数"。
   这是任务本身的局限，不是测试的疏漏。
2. **并发/多线程**未覆盖。程序是单次单线程批处理，不存在并发语义。
3. **> 500 MB 的极端输入**未覆盖。题目已用 2048 MB 内存红线划定了合理范围，
   且大规模输入由分块估计保证耗时上界。

## 六、单元测试自动化

一条命令跑全量：

```bash
python -m pytest
```

每次 push 到 GitHub 都会触发 `.github/workflows/tests.yml` 自动跑测试（等价于
题目所说的"在每日构建中运行单元测试"），失败会在仓库页面标红，方便及时发现。
